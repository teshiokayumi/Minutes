今日やること

前半30分はパソコンを開かずに、紙とペンで「何を作るか」を決めます。後半は、研修のアンケートと議事録を Claude Code に読ませて、次の仕事でそのまま使えるまとめ（コンテキスト資料）を作るコマンド /context を作ります。

作った道具とまとめは自分のパソコンに残り、Web には公開しません。ただし、AI が資料を読むときは、中身が AI のサービス（Anthropic 社）へ送られて処理されます。社外秘のものは入れないでください。

CLAUDE_追記ルール.md
## このプロジェクトの目的（11月回）

アンケートや議事録などの「生の資料」を、次の仕事でくり返し使える**コンテキスト資料**に変えて、手元にためていくためのプロジェクトです。

## フォルダの役割

- `input/` … もとの資料（アンケート・議事録）。**書き換えない**
- `context/` … まとめたコンテキスト資料。ここだけが成果物
- `.claude/commands/` … 手順書（スラッシュコマンド）

## 境界ルール（やってはいけないこと）

- `input/` の元ファイルを書き換えない
- `/context` の実行中は、`input/` と `context/` 以外のファイルを書き換えない（ルールや手順書を変えるのは、人が頼んだときだけ）
- メール送信・外部サービスへの投稿など、外に送る操作はしない
- 資料にない数字・意見を推測で作らない。わからないことは「【要確認】」と書く
- まとめには個人名・電話番号・メールアドレスを残さない（Aさん・Bさんに置きかえる）
- 保存・確定の前には、必ず人間に確認する

## 公開についての約束

- このプロジェクトは **Web に公開しない**（Vercel などにデプロイしない）
- `input/` と `context/` は本物の個人情報が入りうるため、Git の記録に含めない（`.gitignore` で除外する）
- 共有するのは「手順書」と「テンプレート」だけ。中身は各自の手元に置く

## 話し方

- 受講者はプログラミング初心者。専門用語は最小限にして、日本語でわかりやすく説明する
- コードを書く前に、実装方針を3行で説明する

なぜ .gitignore に入れるの？

input/ と context/ には、本物のアンケートや議事録を入れることになります。GitHub に上げると、公開リポジトリなら誰でも見られる状態になります。.gitignore に書いておけば、共有されるのは「手順書」と「テンプレート」だけ。前回やった「Vercel のプロジェクトを削除する手順」と同じ考え方で、公開しない／公開してしまったら止めるをセットで覚えてください。

context.md
---
description: アンケートと議事録を読み、次に使えるコンテキスト資料にまとめて、人に確認してから保存する
argument-hint: [まとめたい資料のパス（省略すると input フォルダの新しい2件）]
---

あなたは、研修やイベントのふりかえりを担当するアシスタントです。
以下の手順を、上から順番に、1つずつ実行してください。

## 手順

### 1. 資料を読む（認識）
- 読むファイル: $ARGUMENTS
- 何も指定されていなければ、`input/` フォルダの中で新しい順に2件（アンケートと議事録）を読む。
- 読んだファイル名を最初に1行で伝える。

### 2. 方針を3行で伝える（考える余白）
- いきなりまとめを書かない。
- 「どんな資料か」「足りない情報は何か」「どうまとめるか」を3行で先に書く。

### 3. 事実と意見を分ける（推論）
- 数えられるもの（回答数・満足度・件数）は、実際に数える。推測で数字を作らない。
- 自由記述は、似た意見をまとめて「何件あったか」を添える。
- 議事録からは「決まったこと」と「まだ決まっていないこと」を分けて拾う。
- 資料に書かれていないことは書かない。判断できないものは「【要確認】」と書く。

### 4. 個人情報を取りのぞく（境界）
- 個人名は「Aさん」「Bさん」に置きかえる。
- 電話番号・メールアドレス・住所は残さず削除する。
- 個人が特定できそうな書き方（一人しかいない所属＋役職など）は、ぼかして書く。

### 5. テンプレートに流し込む（行動の準備）
- `context/_テンプレート.md` の見出しをそのまま使ってまとめる。
- 各項目は、あとで読む人がそれだけ読めばわかるように書く。

### 6. 自分でチェックする（内省）
下書きを、次のチェック項目で自己採点する。結果は ✅ / ⚠️ で一覧にする。

- [ ] 件数の合計が、もとの回答数と合っているか
- [ ] 個人名・電話番号・メールアドレスが残っていないか
- [ ] 資料にない情報を推測で書いていないか
- [ ] 「決まったこと」と「未決」が混ざっていないか
- [ ] 次のアクションに「誰が・いつまでに」が入っているか
- [ ] テンプレートの見出しがすべて埋まっているか（埋められない所は【要確認】）

⚠️ があれば、直せるものは直す。直せないものは、人間への質問にする。

### 7. 人に確認する（Human-in-the-Loop）
- 完成した下書きとチェック結果を見せる。
- 最後に必ず次のように聞いて、返事を待つ。
  「この内容で保存してよいですか？ 直したいところがあれば教えてください。」
- 人間が OK と言うまで、ファイルを保存しない。

### 8. 保存する（行動）
- OK が出たら `context/日付-タイトル.md`（例: `context/2026-09-13-研修ふりかえり.md`）に保存する。
- 保存したファイル名を伝えて終了する。

## やってはいけないこと
- `input/` の元の資料を書き換えること
- メール送信・チャット投稿など、外部に送ること
- 資料にない数字や意見を作ること
- 個人名・連絡先をまとめに残すこと
- 人間の OK なしに保存すること

大事な話

今日のツールは Web に公開しません。9月に作った Web アプリを公開したままの方は、顧客名や社内情報が入っていないか確認し、入っていたら前回の手順でプロジェクトを削除してください。

本物の資料を扱うときは、「公開しない」「共有するのは手順書だけ」に加えて、「社外秘のものは AI に入れない」を守ってください。

今日の持ち帰り

  1. 紙に書ければ、作れる。困りごと → 手順 → 実行者 → 要件。ここまで紙で書ければ、あとは AI に渡すだけ。
  2. 1回整えたものを、使い回す。速くて、ぶれなくて、安全。
  3. 公開しない・人が確認する。最後は人が OK を出す。

数字が合わない・資料にないことが入っている「件数をもう一度数え直してください」「資料にないことは入れないでください」と伝える
エラーが出たエラーの全文を貼り付けて「原因を1つに絞って修正してください」と頼む
途中のステップで遅れた完成版/ フォルダの中身をそれぞれの場所にコピーして追いつく（下のプロンプト）
デスクトップ版でスラッシュコマンドが使えないcontext.md の中身を貼り付けて「この手順で input フォルダの資料をまとめてください」と頼む
Claude Code遅れたときの追いつき
完成版/README.md を読んで、そこに書かれているとおりに、完成版のファイルをそれぞれの場所にコピーしてください。出力例はコピーしなくて大丈夫です。
